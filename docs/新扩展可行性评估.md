# 新扩展可行性评估（基于 easyScholar 注入逻辑 + ShowJCR 数据）

> 结论先行：**可行性高（约 8/10）**。两个仓库恰好互补：easyScholar 提供"在文献网页上标注"的完整工程范式，ShowJCR 提供"离线期刊分区/IF 数据"。两者耦合点仅一处——把 easyScholar 的服务端 API 调用替换为本地数据查表。

## 1. 可行性论证

### 1.1 需求-供给高度吻合

easyScholar 收费的本质 = 服务端 `listPublicationRank9` 接口收费。ShowJCR 的数据表与该接口返回的等级字段几乎一一对应：

| easyScholar 等级 key | 徽章文本 | ShowJCR 数据 |
|---|---|---|
| `sciUp` | 中科院升级版分区 | `FQBJCR2025`（大类分区/Top/小类） |
| `sci` | SCI 分区（JCR Quartile） | `JCR2025`（IF Quartile） |
| `sciif` | IF 值 | `JCR2025`（IF(2025)） |
| `sciif5` | 5 年 IF | ShowJCR **无此数据**（缺口） |
| `jci` | JCI | ShowJCR **无此数据**（缺口） |
| `xr` / `xrTop` / `xrWarn` | 新锐分区 | `XR2026`（大类新锐分区/Top/预警标记） |
| `ccf` | CCF 类别 | `CCF2026` |
| `sciwarn` | 中科院预警 | `GJQKYJMD2025` |

主流需求（中科院分区 + JCR IF/分区 + 新锐）全部可覆盖；5 年 IF 与 JCI 是数据缺口（需另找 JCR 完整导出或放弃这两个徽章）。

### 1.2 注入逻辑与数据源天然解耦

`utils.js` 的管线是 `采集(纯 DOM) → 请求(唯一的外部依赖) → 渲染(纯 DOM)`。替换方案只需实现一个与 `listPublicationRank9` 返回结构兼容的本地查询函数：

```js
// 伪代码：替代 chrome.runtime.sendMessage({action:"getPapersRank"})
function queryLocalRank(publicationName /* {paperID: 期刊名} */) {
  const rows = [];
  for (const [tempID, name] of Object.entries(publicationName)) {
    const hit = DB[normalize(name)];          // 归一化刊名 → 合并记录
    if (hit) rows.push({ tempID, ...hit });   // 字段名对齐 ie 渲染映射
  }
  return { code: 200, data: { publicationRankList: rows } };
}
```

渲染层（`ie` 映射 + badge CSS）可基本原样保留。

### 1.3 技术风险均可控

| 风险 | 等级 | 应对 |
|---|---|---|
| 期刊名缩写匹配（页面常给 "NAT COMMUN"，库是全称） | **高** | ① 归一化（去标点/大小写）精确匹配；② 词首字母缩略词展开（NAT COMMUN→NATURE COMMUNICATIONS 需缩写词典，可引入 NLM 数据或自建映射）；③ 降级 fuzzy（参考 `py/query.py` 的 fuzzywuzzy 思路）；④ 页面 DOM 常同时含全称与缩写，优先抓全称 |
| 站点选择器失效（CNKI/Scopus 等频繁改版） | 中 | 先支持 10–20 个稳定核心站点（Google Scholar、Pubmed、Web of Science、百度学术、CNKI、万方等），逐步移植 157 个 |
| 数据更新滞后 | 低 | ShowJCR 社区每年更新（JCR 6 月、中科院年末、新锐 3 月）；做"数据版本号+一键导入新 JSON"即可 |
| 体积 | 低 | 核心三表精简为 JSON 约 3–6 MB，MV3 扩展可接受 |
| 法律合规 | 低-中 | GPLv3 约束代码（衍生开源即可）；数据再分发的公开上架风险见《ShowJCR-数据资产说明.md》第 5 节 |
| Firefox/Chrome 差异 | 低 | easyScholar 本身即 MV3 + gecko id，可双端；本地查表不涉跨域，host_permissions 可大幅减少 |

## 2. 推荐实现路径

### 阶段 0：数据管线（无浏览器知识依赖，先做）
1. 用 Python/Node 写构建脚本：CSV → 精简 JSON
   - `FQBJCR2025` 抽：Journal、ISSN/EISSN、大类、大类分区、Top、Web of Science、小类1+分区
   - `JCR2025` 抽：Journal、ISSN、eISSN、IF(2025)、Category_1、IF Quartile(2025)_1（或保留多学科的 worst/best）
   - `XR2026` 抽：Journal、大类中文名、大类新锐分区、Top、预警标记
   - `GJQKYJMD2025`、`CCF2026` 全量（小）
2. 以 `NAMES`（全部刊名数组）+ `MAP`（归一化键→合并记录）双结构输出；可选 GZIP（Web Extension 可用 `DecompressionStream` 解压）。

### 阶段 1：MVP（1 个站点 + 徽章）
- 选 **Google Scholar** 或 **Pubmed**（DOM 最稳、easyScholar 选择器现成）。
- 复刻：占位 span 插入 → 本地查表 → badge 渲染 → 2500ms 轮询重扫。
- 设置页：勾选要显示的等级、颜色自定义（结构参考 easyScholar popup）。

### 阶段 2：站点扩展 + 匹配增强
- 按使用频率移植 easyScholar 站点函数（每个仅需验证/微调选择器）。
- 缩写词典 + fuzzy 兜底；未命中期刊提供"点击上报/手动修正"。

### 阶段 3：打磨
- 数据更新机制（检查新数据版本、导入新 JSON）。
- 可选功能：新锐预警红标、CCF 会议标注（XMOL/DBLP 场景）、翻译（easyScholar 的翻译代理可整体跳过或按需保留免费源）。

## 3. 工作量估算（单人，业余时间）

| 阶段 | 预估 |
|---|---|
| 0 数据管线 | 0.5–1 天 |
| 1 MVP | 1–2 天 |
| 2 站点移植（20 个站点） | 1 周（大头在选择器验证） |
| 3 打磨发布 | 2–3 天 |

## 4. 替代/降级方案

- **只要查询工具**：直接用 ShowJCR.exe（release 已有 Windows 版），零开发。
- **Zotero 用户**：可先做 Zotero 插件而非浏览器扩展（easyScholar 的 CDN 拦截提示里也提到 Zotero 生态），复用同一数据管线。
- **退一步的匹配**：若缩写匹配做不好，可先只支持"详情页"（期刊名全称出现处）标注，列表页仅对全称命中的条目标注。
